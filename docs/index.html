RainDB

Embedded OLAP-oriented database engine for .NET — columnar analytics, single-process, low latency. SQL (and planned LINQ) compile to a shared physical-plan intermediate representation, inspired by DuckDB’s embedded analytics model without leaving the .NET ecosystem.

Disclaimer RainDB is an experimental, work-in-progress prototype built with the help of “vibe coding”. Things will break. Features are missing, build scripts may not work, and the engine is not stable enough for production use today. Treat APIs, on-disk formats, and SQL semantics as subject to change.

Purpose & objectives

.NET has excellent row-oriented databases and cloud analytics platforms, but no mature embedded columnar OLAP engine that feels native to the runtime. RainDB fills that gap for services that aggregate telemetry, desktop tools that crunch local datasets, edge nodes that summarize events, and prototypes that should not depend on an external database server.

Why columnar?

Analytical workloads dominate memory bandwidth and CPU vector units. RainDB keeps hot paths on columnar batches and chunks — not row objects — so scans, filters, and aggregates can be vectorized and parallelized at morsel granularity.

One query IR

SQL and (roadmap) LINQ lower to the same logical and physical plans. Application developers, SQL authors, and contributors optimizing operators all share one execution model instead of divergent translation paths.

Production vision

The target end state is a DuckDB-class embedded OLAP engine: prepared SQL, spill when RAM is exceeded, mmap-first storage, WAL + checkpoint, statistics-informed plans, and enough observability to run inside a real .NET service.

Query execution mechanism

A query moves through compile-time lowering and runtime vectorized execution. Parallel work is scheduled per morsel (one source batch); results merge in deterministic batch order for OLAP semantics.

  1. SQL text Hand-written lexer/parser accepts a strict subset (SELECT, FROM, WHERE, GROUP BY, JOIN, ORDER BY, LIMIT).
  2. Logical IR Relational-shaped plan: table scans, filters, aggregates, join keys — no buffer or execution details.
  3. Binding Resolve catalog names to column ordinals; validate types; emit ColumnCompareFilter and plan shape.
  4. Physical plan VectorizedScanPhysicalPlan, HashAggregatePhysicalPlan, JoinPhysicalPlan, SortTopNPhysicalPlan, …
  5. Vectorized engines Selection vectors + gather projection; hash aggregation; hash/sort-merge join; sort/limit over row locations.
  6. Columnar results IColumnarQueryResult or IAggregateQueryResult; pooled buffers returned on dispose.

Storage is column-oriented: each batch holds one chunk per table column (fixed-width little-endian values or UTF-8 Arrow/length-prefixed layouts). Optional directory-backed persistence writes catalog.json and tables/{id}/*.batch segments on append — an MVP snapshot model, not yet a WAL.

Features (today)

Early prototype on the path to production embedded OLAP. See Implementation Status and Development Roadmap for detail.

Columnar storage

Fixed-width and UTF-8 chunks, nullable bitmaps, 64K–1M row batch sizing, in-memory MemoryTable and catalog with schema versioning.

Vectorized read path

Scan, filter, project, global and grouped aggregates, inner equi-joins (hash and sort-merge), ORDER BY / LIMIT on supported shapes.

Strict SQL subset

Parser/compiler for SELECT / FROM / WHERE / GROUP BY / INNER JOIN / ORDER BY / LIMIT with documented limits — full grammar in the Programming Guide.

Morsel parallelism

Parallel.For or channel-scheduled workers over batches; deterministic merge by source batch index.

Persistence MVP

RainDbEngine.OpenPersistent, export/import catalog snapshots, replace-on-write batch files under a data directory.

SIMD hooks

Optional AVX2 double sum; aligned buffer pool (32-byte) for gather projection; mmap reader for fixed-width column files.
